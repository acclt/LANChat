# LQ Chat Windows 客户端空闲写盘优化方案

日期：2026-08-31。状态：用户确认后已实施 Windows 专用优化，独立版本已构建；验证记录见 `D:\SoftwareFree\LANChat-android-file-actions\LQ-Chat-low-io-说明.md`。

用户已明确不需要保存在线时间。第一阶段只调整 Windows 客户端：普通心跳、最后收到心跳的时间、在线／离线状态和可用内存只更新内存，不再写入数据库，也不定时或在退出时补写这些状态。只有首次发现设备或设备名称、地址确实发生变化时，才保存设备基本资料。保留现有心跳频率、在线判断速度、聊天消息保存方式和数据库安全设置。

取消上一版“每分钟保存设备快照”的方案。正常稳定空闲时，目标是心跳导致的数据库写事务为零；并非承诺 WebView2 缓存、聊天消息或系统其他进程也没有写入。

范围修订：本次不优化安卓版，不修改 Android 前台服务、Activity 生命周期、后台接收、权限、通知或 APK。Windows 和 Android 共用部分 Rust 源码，因此共享文件中的改动必须通过 Windows 专用路径隔离；Android 继续使用现有保存逻辑。独立 Web 服务及其他平台也不在本次优化范围内。下文的新增保存策略、启动处理和停止流程均仅针对 Windows 桌面客户端。

本方案基于实际运行的 `LQ-Chat-0.19-windows.exe` 及其所在源码目录 `D:\SoftwareFree\LANChat-android-file-actions`。当前工作区 `D:\SoftwareFree\LANChat` 的源码版本不同，实施时不能直接把两处代码当成同一版本。方案阶段仅新增本文档；用户确认后，业务代码改动已落在实际运行版本的源码目录，原 EXE 和生产数据库结构均保留。

**1. 已确认的现象与范围**

- 未运行 LQ Chat 的短时采样中，D 盘基本没有写入。
- 打开后保持空闲，D 盘平均写入约 175～205 KiB/s。这个数值是整盘统计，不能全部算到 LQ Chat 名下。
- 通过进程打开的文件确认，实际数据库是 `D:\Data\lanchat\lanchat.db`，不是先前从配置推断的 `D:\Data\lanchat.db`。实施和验证均以运行时实际打开的位置为准，不自动迁移或删除任何数据库。
- 对实际数据库做只读采样：15.02 秒内变更计数增加 38，约 2.53 次/秒；消息表没有新增，设备最后在线时间和可用内存持续变化。
- 实际数据库使用 DELETE 日志模式。当前设备保存函数每次执行独立的 `INSERT OR REPLACE`，没有批量事务或保存间隔。
- 本次已经确认空闲设备状态写入的问题，但没有证明风扇噪声也由它导致；优化后的温度、功耗和风扇变化需另外测量。

**2. 保存策略与默认参数**

| 数据／事件 | 内存与界面 | 数据库 |
|---|---|---|
| 已知设备的普通心跳、重复回复 | 立即更新最后收到时间，不等待数据库 | 不入队、不写入、不启动保存定时器 |
| 首次发现的新设备 | 立即显示、允许连接 | 最长 1 秒合并窗口，仅保存设备 ID、名称、地址 |
| 已知设备的名称、地址变化 | 立即更新连接与显示信息 | 最长 1 秒合并窗口，最终资料未改变则跳过写入 |
| 可用内存变化 | 继续使用实时值，不影响传输参数读取 | 不保存，不随其他资料更新附带写入 |
| 上线、离线、重新上线 | 保持现有 2 秒心跳和超过 5 秒未见的判断规则 | 不保存；同一设备资料未变时，重新上线也不写入 |
| 聊天消息、文件消息、发送状态、本机手动设置 | 保持原行为 | 保持原有及时保存，不进入设备合并队列 |
| 用户主动删除设备及聊天记录 | 成功后更新界面 | 明确的删除事务，成功后才向调用方报告成功 |
| 真正退出应用／停止后台核心 | 停止接收新的状态更新 | 仅尽力保存尚未提交的新设备或资料修改，等待上限建议 2 秒；不保存在线时间或其他临时状态 |
| Windows 关闭窗口到托盘 | 核心继续工作 | 不额外保存设备，不重复启动保存任务 |

不设置周期性设备保存任务。只有新设备、资料修改、失败重试或正常退出时存在尚未保存的资料，才唤醒设备保存器。1 秒合并窗口从首次待保存资料变化开始计算，重复相同心跳不能重置窗口或制造新任务；没有资料变化时，保存器休眠，既不执行写事务，也不轮询数据库。

数据库保存失败或进程被强制结束时，上述时间目标不构成保证。首次发现或资料修改后 1 秒内直接被终止，可能来不及保存这次资料变更，下一次收到心跳可以重新发现并保存。在线时间和内存数值本来就不要求在退出后恢复，不存在等待它们定时保存的问题。本改动不扩大聊天消息原有的保存窗口。

**3. 实现结构**

接收心跳后的流程改为：

1. 校验数据，识别设备，立即更新 `PeerManager` 中的实时状态。
2. 比较设备 ID、名称和地址。已知设备资料相同则不触碰保存器；只有新设备或资料变化才更新待保存集合，每台设备只保留最新资料。最后收到时间、在线状态和内存数值不参与资料差异比较。
3. 按现有规则通知界面、处理重新上线后的消息补发；这些步骤不再等待设备历史写盘。
4. 事件驱动的设备保存任务在资料合并窗口到期时取出最新资料，再与已成功保存的版本比较；如果期间变化又恢复到原值，则取消这次无效写入。
5. 在同一个短事务中批量更新确实改变的设备基本资料；提交成功后确认相应资料版本已保存。

新增一个小型设备保存模块（拟名 `peer_persistence.rs`），仅由 Windows 桌面网络核心的生命周期持有。每个运行中的数据库／核心实例只启动一个保存任务，不给每台设备、每次心跳或每次 UI 重建创建定时器。

平台边界使用 `target_os = "windows"`，并由 Windows 桌面入口启用仅在资料变化时保存的策略；不能仅用 `feature = "desktop"` 区分，因为 Android 构建也可能启用该特性。共享的心跳解析与内存更新继续复用，Windows 选择新的设备资料保存器；Android、独立 Web 服务和其他入口继续原有调用路径，不接入新保存器或新退出逻辑。保留现有设备保存函数供原路径使用，新增 Windows 资料批量方法，避免直接替换共享函数导致安卓版行为变化。

待保存集合以设备 ID 为键，内存开销随发生资料变化的设备数增长，不随心跳包数增长。唤醒通知允许合并，不使用无界的“每包一条”消息队列。重连不等同于新设备，不能沿用现有“新设备或重新上线”的布尔值直接决定是否保存。名称或地址确实频繁变化仍可能产生写入，例如同设备多网卡地址切换；应单独记录这类资料变化，不能把它与普通相同心跳混淆，也不能为了降写盘延迟内存里的实际连接地址更新。

Windows 新方法使用只更新 `name`、`addr` 的 `INSERT ... ON CONFLICT(id) DO UPDATE`，按字段差异跳过无变化记录；一批资料使用一个事务。现有 Android 保存函数保持不变。

第一阶段保留现有表结构，不删除 `last_seen`、`is_offline`、`available_memory_mb` 字段，以兼容旧版本。新增设备在这些旧字段中填入约定的未知／离线占位值（`last_seen=0`、`is_offline=1`、`available_memory_mb=0`）；已存在设备只更新基本资料，旧的临时状态字段不再更新，Windows 读取时忽略其在线含义。不得把 0 时间显示为真实的 1970 年在线时间，也不批量清空旧字段制造额外写入。

不迁移数据库、不启用 WAL、不更改 synchronous 设置，不通过关闭刷盘保证来获得性能。查询失败、消息保存失败的处理策略不被这个模块偷偷改变。

**4. 并发、删除与异常处理**

- 每个待保存设备资料携带版本号。取出资料后若名称或地址再变化，提交旧版本只能确认旧版本，不能清除新版本的待保存标记。普通心跳不会生成新的资料版本。
- 获取内存快照时短暂持锁，执行数据库操作时不持有设备表锁。网络接收不能因为数据库锁等待而停止处理心跳。
- 设备保存与主动删除共用串行的设备写入口。删除开始时作废该设备的旧待写版本，等待已开始的设备写操作结束，再在事务中删除设备和对应聊天记录；删除期间的新更新必须有明确的屏障处理，不能插入到删除事务之后。
- 删除成功后，旧快照不得重新插回设备。以后收到真正的新心跳，仍允许按现有“重新发现”规则出现；本优化不把“删除”改成“永久屏蔽”。删除失败返回错误，不把未成功的删除报告为完成，恢复必要的内存状态与待保存状态。
- 设备资料写入失败时保留最新待保存数据，按 5、15、30、60 秒退避重试，之后最多每 60 秒一次，错误日志限频；这是失败重试，不是心跳定时保存。重复心跳不能绕过退避。失败不能再直接使 UDP 发现任务返回并触发整个网络核心退出。
- 若故障是整个数据库不可写，消息保存仍按原有错误处理返回失败，不能对用户宣称消息已安全保存。界面或诊断状态需要能显示“设备历史尚未保存”。
- 保存任务自身 panic 或不可恢复故障需要纳入现有核心监督机制；可恢复的数据库错误在任务内部处理，不伪装成核心崩溃。

**5. Windows 启动、退出与兼容边界**

Windows 客户端真正的新网络会话启动时，只从数据库恢复历史设备基本资料，全部先按离线／待确认处理，实时内存数值视为未知。只有本次会话收到心跳，才认为当前在线；旧数据库里的 `is_offline=false`、最后在线时间、旧地址和旧内存值不能直接证明在线。在线超时判断仍在内存中保留接收时间，并使用本会话的新心跳更新；用户不需要持久化在线时间，不代表可以删除在线判断所需的内存计时。加载历史记录本身不触发逐条重写。该处理在 Windows 新路径内完成，不直接修改共享加载函数以改变 Android 或其他入口的启动语义。

Android Activity、Android CoreRuntime 和独立 Web 服务入口保持原实现。本轮只核对共享代码改动没有破坏它们的编译与原调用路径，不要求它们复用新的保存模块，也不进行跨端生命周期重构。

正常停止顺序为：停止接受新资料更新 → 等待资料生产者停止 → 仅保存尚未提交的基本资料 → 停止保存任务 → 按连接池所有权关闭或释放连接池。没有待写基本资料时，不做任何设备写入，不全量保存在线状态，也不补记退出时间。保存任务不能与网络任务使用同一个“一取消就直接退出”的路径，否则必要的新设备资料保存会被跳过。现有核心停止总时限必须仍然有效。

只有 Windows 托盘“退出”和正常窗口退出需要接入新增的正常停止流程；Web 服务停止信号和 Android 核心停止逻辑不改。共享 CoreRuntime 中新增的保存资源及停止步骤仅在 Windows 桌面策略启用时存在，原路径不等待也不调用新保存任务。强制停止、断电、系统直接杀进程不保证执行退出回调，因此必要的设备基本资料需在正常运行时按事件及时保存，不能都留到退出时。保存超时需在停止结果中区分“进程资源已释放”和“设备资料未全部保存”，不无限等待。

不改变心跳报文格式、端口、设备 ID、消息协议或文件协议，现有 Android 客户端作为对端即可继续互通，无需升级或重新打包 APK。实际数据库位置不变，不能误用此前检查到的旧数据库。

**6. 分阶段实施顺序**

第一阶段为本次推荐的完整改动范围：

1. 加入 Windows 设备基本资料保存模块、按字段差异保存的数据库方法和只驻留内存的诊断计数；没有周期性心跳保存任务。
2. 接入心跳接收路径，保留界面通知、在线判断、文件参数读取和消息补发的实时性。
3. 同时完成 Windows 路径的版本确认、删除屏障、启动待确认状态与退出保存；这些不是可后补的正确性项目。保留 Android、独立 Web 服务及其他平台的原路径。
4. 用临时数据库和受控测试设备验证，再构建单独命名的测试版本。保留现有 0.19 可执行文件，不直接覆盖。
5. 做同条件的优化前后采样，记录数据库成功写事务次数及文件级磁盘写入，再判断是否需要第二阶段。

第二阶段也仅针对 Windows，在仍有明显 CPU、网络或 WebView2 活动时评估，单独验证收益；任何会影响 Android 或共享协议的调整都另立范围，不能顺带实施：

- 同一设备经广播、组播和回复重复出现时，合并重复界面通知，但仍刷新必要的在线时间。
- 可用内存为 0 的回复报文目前会覆盖正常心跳中的内存值。需要区分“未知／回复占位值”和有效测量，保留有效值的新鲜度；这也关系到文件分块参数，不能只为减少界面刷新而任意延迟。
- 发送心跳每次读取用户名和自定义设备列表，可改为内存缓存并由设置变更主动失效。
- 前端目前既接收设备事件，又每秒轮询设备列表；先检查是否有重复初始化，再设计后台界面刷新节流。离线判断当前部分依赖列表读取，不能直接停掉轮询而不补上核心侧离线检测。
- 如需缩小广播目标范围，必须保留热点、不同网段、自定义 IP／域名的兼容性，单独做网络测试。
- 只有第一阶段测量后仍证明数据库事务开销是瓶颈，才另行评估 WAL 等数据库参数及备份兼容性；不默认降低同步安全等级。

**7. 验收标准**

测试数据库、测试消息和故障注入使用专门的临时目录，不直接对用户聊天数据库做压力测试、强杀测试或锁冲突测试。

| 场景 | 通过条件 |
|---|---|
| 同样的 2 台在线对端，启动资料保存完成后空闲 10 分钟，设备名称和地址稳定、无新设备、无消息传输 | 普通心跳导致的成功设备写事务为 0 次，最后在线时间和可用内存变化不触发写入；没有定时保存唤醒 |
| 按实测约 2.53 次/秒作为参考 | 目标完全消除普通心跳导致的数据库写入，而非只降低到每分钟一次；不能把这一目标说成整盘写入完全消失 |
| 重复广播、组播、回复 | 不按重复包分别写盘，不重复触发同一次重新上线的补发 |
| 在线／离线与重连 | 保持现有心跳频率和超过 5 秒未见的判断规则；状态判断不依赖数据库在线时间；相同资料的设备重连不写设备表，补发消息另按原方式保存 |
| 文件传输 | 读取本会话实时内存状态和地址，不使用数据库旧状态决定在线连接与传输参数 |
| 新设备发现、名称或地址变化 | 数据库健康且没有异常拥塞时，1 秒合并窗口内提交基本资料；界面显示不等待保存；重复相同资料或窗口内恢复原值不写入 |
| 聊天消息与文件状态 | 原有即时保存和错误反馈正常，不进入设备状态批处理；未确认保存成功的数据不能显示为已安全保存 |
| 保存过程中又收到资料变化 | 最新资料版本不被旧事务完成后的清理误删，后续能写入最新资料；仅心跳时间或内存变化不生成待写版本 |
| 删除与正在保存交错 | 删除成功后旧待写内容不能恢复设备或已删除聊天；之后的新心跳重新发现遵循现有语义 |
| 数据库暂时忙、只读、磁盘错误 | 不停止心跳接收；待写基本资料保留，重试退避，故障可见；恢复后仅保存最新基本资料 |
| 正常退出、强制终止、重启 | 正常退出仅尽力完成未提交的基本资料；没有资料变化则不写设备表；强制终止后数据库可读且消息原有保存保证不退化；新会话不误判历史设备在线 |
